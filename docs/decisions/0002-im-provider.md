# ADR-0002：IM 通过 Provider 抽象，首选自托管

- 状态：已接受
- 日期：2026-11-27

## 背景

候选方案与阶段 0 审计结论：

| 方案 | 结论 |
|---|---|
| 自托管社区版 IM（JuggleIM） | Apache-2.0、只要 MySQL 8、无 Redis/Kafka/ES；社区版除集群外功能齐全；但 2C4G 无实测、Flutter 端缺聊天室/在线态/推送 |
| OpenIM | 客户端 SDK 为 AGPL-3.0，闭源商用不合适；需六组件栈 |
| 腾讯云 IM | 能力最全、小程序官方 SDK；但体验版无已读回执、单群 20 人；数据在云端，7 天漫游且导出窗口仅 7 天 |

## 决策

1. 业务代码只依赖 `chat.Provider`，不 import 任何厂商 SDK；
2. 生产首选**自托管**（社区版 IM，单节点起步）；
3. 若引入 SaaS 做临时验证，必须同时开启**消息双写**（回调落自有库），否则切自托管时
   超出漫游窗口的历史不可恢复；
4. 客户端能力差异由适配层承担：不支持的能力返回 `ErrNotSupported`，由业务降级，不做假实现。

## 后果

- 需要自己运维 IM 服务与 MySQL（备份、恢复演练）；
- 小程序端若无官方 SDK，需要额外适配成本（评估过：约 14–23 人日）；
- 换来的是数据自持与厂商无关，长期成本可控。

## 未决

- 单机 2C4G 的容量上限需实测（RSS / 连接数）；
- 集群/高可用方案（社区版不含）。
